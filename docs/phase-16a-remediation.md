# Phase 16A read boundary remediation

Date: 2026-10-04. Scope: the implemented MCP inspection milestone and the shared code it calls. Proposal, operation, signing, and apply infrastructure from 16B–16D is not part of this remediation.

## Design decisions

### Ownership and storage

Every plan/run lookup verifies canonical source ownership and related stored plan/run associations. A caller-supplied project ID cannot relabel a foreign record. IDs are bounded opaque strings; the project ID includes a hash of the normalized canonical root. Manifest claims are validated but cannot select the server identity or a different source.

Plan creation now records the inspected repository root as `source_root`, even when governance exports use a separate `--output` directory. Older plans that mistakenly recorded their output directory must be regenerated and approved again; their signed identity is not rewritten automatically.

Source, configured state, and configured staging roots are resolved and checked for equality/ancestor overlaps before opening SQLite. The exported preview handler requires an injected store and never creates source-local state. SQLite connections close after each transaction, avoiding lingering handles in a long-running Windows server.

### Actual reads and generated bytes

The filesystem adapter guards path components at the actual script/template/style/manifest/plan read. Links, junctions/reparse points, ignored paths, credential filenames, oversized/binary text, changed files, and credential-shaped content are rejected. Inventory uses the same reader and reports exclusions without exposing skipped secret paths.

The existing fingerprint implementation now rejects links and escaped explicit paths, skips credential files before opening, uses bounded reads and file identity checks, and rejects credential-shaped content. It hashes non-hidden files outside ignored build/dependency directories; known credential files are excluded. Existing preview/apply calls use the same fingerprint rules.

Generated content is checked before a ChangeSet is saved. A credential-bearing artifact is rejected, not silently rewritten. Display results are independently redacted. The plan DTO is `display_only`: a page/redacted view is not an executable approval artifact, and `plan_digest` identifies the authoritative full plan.

Step IDs must belong to the plan. An omitted ID selects a sole step explicitly and reports its ID; multiple-step plans require selection. Expected paths constrain component matching. Framework adapters receive discovered component names, preventing unrelated components sharing a hardcoded identity. Colliding generated paths fail closed.

### Inspection permissions

The trusted local launcher resolves an OS account and creates an immutable `InspectionContext`. The inspection capability policy permits doctor/inventory at Mode C and requires Mode B for plan/run/ChangeSet reads. Launcher configuration can narrow grants or lower assurance. Tool arguments cannot supply actors or grants. This does not mint Mode A signatures or human apply approval.

### Limits and protocol behavior

| Boundary | Limit / behavior |
|---|---|
| Individual source text/fingerprint input | 1,000,000 bytes |
| Inspector aggregate | 10,000 text files and 20,000,000 bytes |
| Fingerprint aggregate | 10,000 non-ignored files and 20,000,000 bytes |
| Inventory/plan page | At most 100 files/steps; explicit total, offset, and `has_more` |
| Preview | 100 generated files and 32,768 generated bytes; reject before persistence |
| Serialized result DTO | 65,536 UTF-8 bytes |
| Incoming SDK params | 65,536 serialized bytes; credential-shaped input rejected |
| SDK result with text and structured views | 147,456 UTF-8 bytes |

Oversized single records/previews fail with a limit error; executable content is never silently truncated. Page requests retrieve remaining inventory files or plan steps. Durable cancellation and bounded evidence/artifact reads remain 16B work.

SDK middleware protects validation errors as well as DTOs. Logs remain on stderr with redaction. Sync interrupts are handled outside `anyio.run`; async cancellation is handled inside the backend. Startup/transport failures follow a defined stderr-only path.
